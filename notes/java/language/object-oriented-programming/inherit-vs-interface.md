# Java 继承与接口实战辨析
> 讨论问题：Java继承使用场景、业务开发中继承与interface如何选择，继承是否主要为框架而生

## 核心结论
继承并不是专门为框架创造的语法特性，但**框架是继承最合适、最广泛的应用场景**；
普通业务系统需求多变，继承耦合风险高，因此日常业务编码中接口 `interface` 使用频率远高于类继承 `extends`。

## 一、基础概念区分
### 类继承 extends（单继承）
1. 语义：严格的 **is-a** 从属关系
2. 作用：同时复用父类 **成员变量(状态)** + 方法实现代码
3. 限制：Java仅支持单继承，耦合度高，存在「脆弱基类」问题

### 接口 interface（多实现）
1. 语义：拥有某种能力 can-do
2. 作用：定义行为契约，不承载状态，面向抽象编程实现解耦
3. 优势：支持多实现，灵活扩展，适配持续变更的业务需求

## 二、为什么框架大量使用继承？
框架特性和继承能力高度契合：
1. 顶层基类结构**长期稳定**，极少大规模修改；
2. 普遍使用**模板方法模式**：父类固定主流程，子类重写扩展逻辑；
3. 需要统一封装大量通用字段、公共方法，子类直接复用；

典型例子：HttpServlet、Netty AbstractHandler、Spring 各类抽象模板类。

## 三、业务开发谨慎使用继承的根本原因
业务系统最大特征：需求持续迭代、逻辑经常变化
1. 父类微小改动，全部子类隐性受到影响，风险不可控；
2. 单继承限制，一旦继承某个父类，丧失拓展其他父类的可能性；
3. 极易出现：早期符合 is-a，后续需求变更，继承关系不再成立。

> 行业规范建议：业务代码尽量避免构建复杂继承链，继承层级最好只保留一层。

## 四、什么时候才允许使用继承？
必须同时满足全部条件：
1. 父子类是**永久稳定、不会变更**的 is-a 关系；
2. 子类需要同时复用父类属性 + 方法实现；
3. 适合模板方法设计模式；

✅ 典型场景：
异常继承体系、框架抽象基类、稳定的数据模型抽象
❌ 不推荐：单纯为了复用代码强行建立继承（优先使用**组合**替代）

## 五、开发选型标准
1. 需要定义行为标准、模块解耦、需要多种能力组合：优先 `interface`
2. 需要复用大量属性与实现，且具备稳定is-a关系：使用抽象类继承
3. 无is-a关系，只想复用工具代码：采用**组合**，杜绝滥用继承

## 六、问题解答：继承是为框架而生的吗？
准确理解：
继承是面向对象基础语法，不是专为框架设计。
但是继承的耦合特性、代码复用能力、适配模板模式的特点，刚好契合框架开发；
业务代码受需求变动制约，很难满足继承严苛的前置条件，所以业务里接口更加普遍。

## 七、最终精简口诀
框架多用抽象继承，业务优先接口组合；
is-a稳定才继承，只为复用别extends。
