# Simple Full-Stack Learning Project Requirement Refinement Loop

我现在有一份简单的前后端分离学习项目需求文档。

项目技术栈：

前端：
- Vue 3
- Axios
- Element Plus

后端：
- Spring Boot 3.5.16
- JDK 17

这是一个用于学习的 Demo 项目，不是企业级生产项目。

我的主要目标是通过这个项目练习：

- Vue 组件和页面开发
- Element Plus 基础组件使用
- Axios 发起 HTTP 请求
- 前后端参数传递
- Spring Boot Controller / Service 等基础分层
- REST API 的基本设计
- JSON 数据交互
- 表单提交
- 数据查询
- 新增、修改、删除等基础 CRUD 流程
- 前后端联调

因此，请避免过度设计。

不要主动引入：

- 微服务
- 分布式架构
- 消息队列
- Redis
- Docker / Kubernetes
- OAuth
- 复杂权限系统
- 复杂设计模式
- 企业级高并发方案

除非原需求明确要求。

# 你的任务

不要直接重新设计整个项目。

请基于我已有的需求文档，通过多轮检查和修改，把它完善到：

> 我可以根据这份需求文档直接开始编写这个学习项目。

重点不是把文档写得非常正式，而是：

- 功能明确
- 页面明确
- 请求明确
- 参数明确
- 返回结果明确
- 前后端流程明确
- 基本异常情况明确

# Requirement Refinement Loop

每一轮按照下面的流程执行。

## Step 1 — Understand

先阅读当前需求文档，并总结：

### 这个项目是做什么的？

用简短的话说明项目目标。

### 用户可以做什么？

列出主要功能。

例如：

- 查询
- 新增
- 修改
- 删除
- 搜索
- 提交表单

只根据已有需求判断，不自行扩展复杂功能。

---

## Step 2 — Check User Flow

检查每个功能的基本使用流程是否清楚。

例如：

用户进入页面

→ 页面通过 Axios 请求后端

→ Spring Boot 接收请求

→ 后端处理数据

→ 返回 JSON

→ Vue 接收数据

→ Element Plus 组件显示结果

检查是否存在：

- 不知道点击哪个按钮
- 不知道提交什么数据
- 不知道操作完成后页面发生什么
- 不知道失败时发生什么

如果存在，指出问题。

---

## Step 3 — Check Frontend Requirements

从 Vue 3 前端角度检查需求。

每个主要功能尽量明确：

### 页面

需要哪些页面？

例如：

- 列表页
- 新增表单
- 编辑表单

如果项目很简单，也可以全部放在一个页面。

### Element Plus 组件

只有在明显适合时才建议组件，例如：

- el-table
- el-form
- el-input
- el-button
- el-dialog
- el-pagination

不要为了使用组件而增加需求。

### 前端数据

检查页面需要保存哪些数据，例如：

- 列表数据
- 表单数据
- 搜索条件
- loading 状态

不要求设计复杂状态管理。

### Axios

检查每个功能是否明确：

- 什么时候发送请求
- 请求方式
- 请求地址
- 请求参数
- 请求成功后做什么
- 请求失败后做什么

---

## Step 4 — Check Backend Requirements

从 Spring Boot 角度检查需求。

每个主要功能检查是否可以对应到清晰的 REST API。

例如：

查询列表：

GET /users

查询单个：

GET /users/{id}

新增：

POST /users

修改：

PUT /users/{id}

删除：

DELETE /users/{id}

这里只是参考。

接口设计应根据实际需求决定，不要为了 REST 风格强行增加接口。

同时检查：

### Controller

Controller 应该接收什么参数？

例如：

- @RequestParam
- @PathVariable
- @RequestBody

### Service

业务逻辑是否足够简单明确？

### 数据对象

需要哪些字段？

每个字段至少明确：

- 字段名
- 基本类型
- 是否必填

不要自行设计复杂 DTO / VO / BO 层，除非确实有学习价值或原需求要求。

---

## Step 5 — Check API Contract

这是本项目重点检查内容。

确保前端和后端对同一个接口的理解一致。

每个主要接口尽量整理为：

### 功能

这个接口做什么。

### Method

GET / POST / PUT / DELETE

### URL

例如：

/api/users

### Request

前端发送什么。

例如：

```json
{
  "name": "Tom",
  "age": 20
}
```

### Response

后端返回什么。

例如：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

如果原需求还没有统一返回结构，不要擅自强制设计复杂规范。

可以提出建议，但标记为：

`[建议]`

---

## Step 6 — Check Necessary Edge Cases

这是学习项目，所以只检查真正必要的情况。

优先考虑：

- 输入为空
- ID 不存在
- 请求参数类型错误
- 新增失败
- 修改失败
- 删除失败
- 后端返回错误
- Axios 请求失败
- 查询结果为空

不要主动设计大量极端生产环境场景。

例如暂时不需要考虑：

- 分布式事务
- 服务熔断
- 多机一致性
- 百万级并发
- 复杂安全攻击模型

除非原需求明确要求。

---

## Step 7 — Find Problems

把当前需求中的问题分为三种。

### Missing

缺少开发所必须的信息。

例如：

“支持修改用户”

但是没有说明：

- 修改哪些字段
- 如何选择用户
- 点击修改后发生什么

### Ambiguous

描述存在多种理解。

例如：

“支持搜索用户”

但是没有说明：

- 按姓名？
- 按 ID？
- 模糊搜索还是精确搜索？

### Overdesign

对于当前学习项目来说过于复杂。

例如只是做 CRUD，却设计：

- MQ
- Redis
- 微服务
- OAuth2
- 多级权限

如果出现，应指出可以简化。

---

## Step 8 — Revise

根据本轮发现的问题修改需求文档。

修改时遵守：

### 1. 保留项目原始学习目标

不要把一个简单 Demo 改造成企业项目。

### 2. 优先简单实现

如果两个方案都能满足学习目标：

优先选择更容易理解和实现的方案。

### 3. 不擅自创造业务规则

例如原需求没有规定：

“用户名最长 20 个字符”

不要直接写成确定需求。

应该写：

`[待确认：用户名是否需要长度限制？]`

### 4. 技术细节服务于学习目标

可以补充：

- Axios 请求方式
- Controller 参数接收方式
- JSON 示例
- 页面交互

但不要大量添加与当前学习目标无关的架构设计。

---

# Step 9 — Development Readiness Check

修改完成后检查：

### 功能

我是否已经知道项目有哪些功能？

### 页面

我是否知道前端需要写哪些页面或组件？

### 请求

我是否知道每个按钮会触发什么 Axios 请求？

### API

我是否知道主要接口的：

- Method
- URL
- 参数
- 返回值

### 后端

我是否能够大致确定：

Controller
→ Service
→ 数据访问

应该如何组织？

### 联调

我是否能够清楚描述一次完整的数据流？

例如：

用户点击“查询”

→ Vue 调用方法

→ Axios 发送 GET 请求

→ Spring Boot Controller 接收

→ Service 处理

→ 返回 JSON

→ Axios 得到响应

→ Vue 更新数据

→ el-table 重新渲染

如果这些主要问题已经明确，则可以结束 Loop。

Spring Boot 3.5.16 + JDK 17

`READY`

# 最重要的原则

整个 Loop 始终遵守：

**Simple first.**

这是学习项目。

目标不是设计一个最完整的商业系统，而是：

> 用尽可能清楚、简单、可实现的需求，把一次完整的 Vue → Axios → HTTP → Spring Boot → JSON → Vue 前后端交互流程真正学明白。

如果某个需求：

- 不影响核心功能
- 不影响前后端联调
- 不明显增加学习价值

优先不增加。
