# MySQL 索引为什么能提高查询速度，但会降低更新性能

## 一句话理解

可以把 MySQL 的索引理解成一本书的**目录**：

> **查询变快**：因为可以通过目录快速定位数据，不需要从头到尾扫描。  
> **更新变慢**：因为修改正文以后，相关的目录也可能需要一起修改。

在 MySQL InnoDB 中，这个“目录”通常就是 **B+ Tree 索引**。

---

## 1. 为什么索引能提高查询速度？

假设有一张 `student` 表，有 1000 万条数据：

| id | name | age |
|---|---|---|
| 1 | Tom | 18 |
| 2 | Jack | 20 |
| ... | ... | ... |
| 10000000 | Alice | 22 |

执行：

```sql
SELECT *
FROM student
WHERE age = 22;
```

### 1.1 没有 `age` 索引

MySQL 基本上只能：

```text
第1行 age是不是22？
↓
第2行 age是不是22？
↓
第3行...
↓
...
↓
第1000万行
```

也就是 **全表扫描**。

可以粗略理解为：

```text
时间复杂度：O(n)
```

数据越多，扫描成本越大。

---

### 1.2 给 `age` 建索引

```sql
CREATE INDEX idx_age ON student(age);
```

InnoDB 会维护一棵类似这样的 B+ Tree：

```text
                    [20 | 25]
                   /    |    \
                  /     |     \
              <20     20~25    >25
               |        |
          [18 19]   [20 21 22 23]
                           ↑
                        找到22
```

查找 `age = 22` 时，不再扫描 1000 万行，而是沿着 B+ Tree 一层层向下定位。

可以粗略理解为：

```text
全表扫描：

1000万条
↓
逐条比较
↓
找到结果


B+ Tree：

根节点
↓
中间节点
↓
叶子节点
↓
找到 age = 22
```

B+ Tree 通常只有很少几层。

例如一个非常大的表，索引树可能也只有 **3～4 层**。

所以查询可能从：

```text
检查几百万条记录
```

变成：

```text
访问几个索引页
+
读取对应数据
```

**本质：**

> 索引用额外的数据结构，减少了查找数据时需要扫描的数据量。

---

## 2. 为什么索引会降低 INSERT / UPDATE / DELETE 的性能？

因为索引不是凭空存在的。

数据库除了维护表数据，还要维护：

```text
PRIMARY KEY 索引
idx_age 索引
idx_name 索引
idx_xxx ...
```

例如现在有三个索引：

```sql
PRIMARY KEY(id)

INDEX idx_age(age)

INDEX idx_name(name)
```

一条记录实际上对应多个数据结构：

```text
                  student
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
   主键索引       age索引       name索引
```

所以写入数据时，不是简单修改一次。

---

## 3. INSERT 为什么会变慢？

假设执行：

```sql
INSERT INTO student(id, name, age)
VALUES (10001, 'Tom', 22);
```

如果没有额外索引：

```text
写入数据
   ↓
维护主键索引
```

但如果还有：

```text
INDEX(age)
INDEX(name)
```

那么 MySQL 还需要：

```text
插入 student 数据
        ↓
维护 PRIMARY KEY B+ Tree
        ↓
维护 idx_age B+ Tree
        ↓
维护 idx_name B+ Tree
```

例如 `age = 22` 必须插入 `idx_age` B+ Tree 的正确位置：

```text
原来：

18 → 20 → 21 → 23 → 25

插入22：

18 → 20 → 21 → 22 → 23 → 25
                  ↑
              找位置插进去
```

因此：

> **索引越多，一次 INSERT 需要维护的 B+ Tree 就越多。**

---

## 4. UPDATE 为什么会变慢？

假设执行：

```sql
UPDATE student
SET age = 23
WHERE id = 100;
```

原数据：

```text
id = 100
age = 22
```

现在：

```text
age: 22 → 23
```

如果 `age` 没有索引，主要就是修改数据。

但如果存在：

```sql
INDEX idx_age(age)
```

那么不能只修改表数据。

因为索引里原来还有：

```text
22 → id=100
```

必须把旧索引记录删除，再插入新的索引记录：

```text
旧：

idx_age

18
20
21
22 ──→ id=100
23
25


UPDATE age = 23


第一步：

删除：

22 ──→ id=100


第二步：

插入：

23 ──→ id=100
```

所以一次：

```sql
UPDATE age
```

实际上可能相当于：

```text
修改记录
+
删除旧索引项
+
插入新索引项
```

索引越多，维护成本越高。

---

## 5. 如果 UPDATE 的字段没有索引呢？

这是一个很重要的区别。

比如存在：

```sql
INDEX idx_age(age);
```

但是执行：

```sql
UPDATE student
SET name = 'Jack'
WHERE id = 100;
```

如果 `name` 没有索引：

```text
age没有变化
↓
idx_age通常不需要改变
```

所以：

> 并不是 UPDATE 任意字段都会导致所有索引重建。

主要规律是：

```text
修改了哪个索引涉及的字段
              ↓
相关索引需要维护
```

例如：

```text
索引：

idx_age(age)
idx_name(name)
idx_age_name(age, name)
```

执行：

```sql
UPDATE student
SET age = 30
WHERE id = 1;
```

影响情况：

```text
idx_age          ✓
idx_name         ✗
idx_age_name     ✓
```

---

## 6. 索引也可能让 UPDATE 更快

例如：

```sql
UPDATE student
SET score = 100
WHERE id = 8888888;
```

UPDATE 实际上可以分成两个阶段：

```text
① 找到数据
② 修改数据
```

如果 `id` 有索引：

```text
WHERE id = 8888888
       ↓
快速定位
```

索引会让第一阶段变快。

因此严格地说：

> **索引不是简单地“让 UPDATE 变慢”。**

更准确的理解：

```text
UPDATE
│
├── 查找目标记录
│      ↑
│    索引可能加速
│
└── 修改记录
       ↓
   索引需要维护
       ↓
   增加写操作成本
```

最终到底快还是慢，需要看具体 SQL。

---

## 7. B+ Tree 维护的额外成本：页分裂

InnoDB 的索引是按 **Page（页）** 存储的。

InnoDB 默认页大小通常是：

```text
16 KB
```

假设一个索引叶子页：

```text
┌──────────────────────┐
│ 10 20 30 40 50 60 70 │
└──────────────────────┘
```

现在需要插入：

```text
35
```

目标位置：

```text
10 20 30 [35] 40 50 60 70
```

如果当前页空间不够，可能发生：

```text
             原页面
        10 20 30 40 50 60
                 ↓

               分裂

        Page A        Page B
       10 20 30      35 40 50 60
```

这叫：

> **Page Split（页分裂）**

页分裂会产生更多：

- 页面修改
- 数据移动
- B+ Tree 调整
- Buffer Pool / 磁盘 I/O 开销

所以索引写入并不是免费的。

---

## 8. DELETE 也是同样的道理

例如：

```sql
DELETE FROM student
WHERE id = 100;
```

如果这条记录出现在：

```text
PRIMARY KEY
idx_age
idx_name
idx_age_name
```

那么删除数据时需要：

```text
删除记录
   ↓
维护主键索引
   ↓
维护 age 索引
   ↓
维护 name 索引
   ↓
维护联合索引
```

所以索引越多：

```text
INSERT
UPDATE
DELETE
```

整体的写入成本通常越高。

---

## 9. 索引的本质：空间换时间

这是理解索引最重要的一句话：

> **索引的本质是通过额外的存储空间和写入维护成本，换取查询速度。**

关系如下：

```text
                建立索引
                   │
            ┌──────┴──────┐
            ↓             ↓
          好处            代价
            │             │
       SELECT更快      占额外空间
       WHERE更快       INSERT更慢
       JOIN更快        DELETE更慢
       ORDER BY可能更快 UPDATE可能更慢
                     维护B+Tree
```

---

## 10. 现实类比：学生档案和目录

假设学校有 **100 万个学生档案**。

### 没有索引

所有档案放在一个巨大箱子里：

```text
找“张三”
↓
第1份
第2份
第3份
...
第800000份
↓
找到
```

查询很慢。

但是新增学生很简单：

```text
拿一份新档案
↓
放进去
```

---

### 有索引

建立一本：

```text
姓名目录

Alice → 柜子001
Bob   → 柜子017
Jack  → 柜子293
Tom   → 柜子581
...
```

查询：

```text
Tom
↓
查目录
↓
柜子581
↓
直接取出
```

很快。

但是新来了一个：

```text
Mike
```

不能只保存档案，还需要：

```text
① 保存 Mike 的档案
② 更新姓名目录
③ 更新年龄目录
④ 更新班级目录
⑤ 更新学号目录
...
```

因此：

> **目录越多，查询越方便；但每次数据发生变化，需要维护的目录也越多。**

---

## 11. 最终关系图

```text
                     INDEX
                       │
              ┌────────┴────────┐
              ↓                 ↓
           查询阶段            写入阶段
              │                 │
         减少扫描范围        维护索引结构
              │                 │
         B+ Tree定位        B+ Tree插入/删除
              │                 │
            更快              更慢
              │                 │
          SELECT ↑      INSERT / UPDATE /
                       DELETE 成本 ↑
```

---

## 12. 最终结论

### 查询方面

索引通过 **B+ Tree 等数据结构快速定位数据**，避免大量全表扫描，因此能显著提高查询效率。

### 写入方面

INSERT、UPDATE、DELETE 除了修改表数据之外，还需要维护相关索引，因此会带来额外的：

- B+ Tree 查找
- 索引项插入
- 索引项删除
- 页面修改
- 页分裂
- Buffer Pool / 磁盘 I/O

因此索引越多，写入成本通常越高。

### 实际设计原则

> **索引并不是越多越好。**

应该优先给经常用于以下场景的字段建立合适索引：

- `WHERE`
- `JOIN`
- `ORDER BY`
- `GROUP BY`

而不要为了“可能有用”给每个字段都建索引。

对于 `UPDATE`，可以记住这个更精确的结论：

> **索引可以加速 UPDATE 的“查找目标记录”阶段，但如果更新涉及索引字段，又会增加“修改和维护索引”阶段的成本。**
